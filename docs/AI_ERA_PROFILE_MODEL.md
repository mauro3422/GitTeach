# GitTeach AI-era profile model

## Product thesis

GitTeach is not a code-authorship detector and not a semantic code-search engine. Its job is to build a personalized, evidence-backed professional profile from the observable shape of a developer's work.

The core question is not `who typed each line?`. In AI-assisted development that question is often unknowable and increasingly unimportant. The product asks instead:

> What does this person repeatedly build, maintain, verify, automate, review, ship and care about across projects?

GitTeach must remain useful when code, tests, documentation or even commits were partially or largely generated by AI.

## Independent product boundary

The shipped product is a standalone web/app experience. A normal user connects GitHub/Git repositories and optionally other authorized profile sources. GitTeach may have its own conversational LLM, but it does not code for the user.

Bridge, MSSR and OmnySys are development infrastructure or optional external sources only. They are not runtime requirements and the product must never assume that a user has agent telemetry.

WidgetForge is a presentation layer: it can turn GitTeach profile statistics and tendencies into README/profile widgets, timelines, charts, cards and playful visualizations.

## Three evidence planes

### 1. Deterministic repository and GitHub facts

These should be extracted without Jev whenever possible:

- languages and language evolution;
- frameworks, runtimes, package managers and build tools;
- repository/project age, recency and longevity;
- commit/activity cadence without treating volume as skill;
- source/test/doc/tooling file distributions;
- CI workflows, lint/typecheck/static-analysis gates;
- releases, tags, packages and deployment workflows;
- issues, pull requests, reviews and contributors when authorized/available;
- test/benchmark infrastructure;
- automation scripts and generators;
- changelogs, architecture docs and ADR-like material;
- project type signals: app, library, CLI, IDE/tooling, game, mod, API, automation, etc.;
- maintenance signals: repeated returns to a project/subsystem, fixes after releases, migrations and compatibility work.

GitHub already exposes contribution/activity and repository statistics through its APIs; these are useful inputs but remain measurements, not expertise scores.

The first delivery/maintenance contracts are now implemented as shared JS/Rust `giteach-repository-lifecycle-v1` and `giteach-portfolio-lifecycle-v1`. The repository contract records first/latest commit, active calendar months/years, local Git tags reachable from the current `HEAD`, and commits after the latest reachable tag. The portfolio contract aggregates those facts once per independent repository. A local Git tag is not treated as a GitHub Release, and post-tag activity is a factual sequence rather than evidence of quality, ownership or seniority.

Connected GitHub facts are also implemented as shared JS/Rust `giteach-github-repository-facts-v1`. Releases, PRs, reviews and true issues retain stable provenance and remain separate from local Git facts. For a connected identity, an authored PR can support contribution (`identity-linked`) while a submitted review can support review agency; pending reviews and release/issue activity remain factual observations rather than fabricated personal engineering actions.

### 2. Cross-project tendencies

GitTeach becomes personal when it compares independent projects over time. A tendency needs repeated support, not one isolated file.

Candidate tendencies include:

- automation-oriented development;
- testing/verification-oriented development;
- tool-building / developer-tooling focus;
- documentation discipline;
- observability/instrumentation tendency;
- modularization/refactoring tendency;
- performance/benchmark orientation;
- long-term maintenance tendency;
- rapid experimentation/prototyping;
- release/delivery discipline;
- game/tooling, web, systems, graphics, AI or other recurring domains;
- AI-assisted/supervisory workflow when there is sufficient evidence or user confirmation.

The first implemented deterministic contract is `giteach-development-tendencies-v1` in JavaScript and Rust. It currently covers testing/verification, automation, documentation, tooling/configuration and CI/delivery. Presence is counted once per independent repository, requires support from at least two repositories, and stores one representative evidence reference per supporting repository; file volume never increases the prevalence value.
These are descriptive profile dimensions. GitTeach must not collapse them into `87% programmer`, `senior score`, IQ-like ranks or opaque quality ratings.

## Supervisory engineering in the AI era

When AI can generate code, valuable human work shifts toward intent, constraints, selection, correction, verification and ownership of outcomes.

GitTeach should therefore look for observable proxies of supervisory engineering even when no agent logs exist:

- features repeatedly followed by tests or regression coverage;
- bug-fix/revert/rework loops;
- review and requested-correction activity;
- migrations with compatibility checks;
- benchmarks before/after changes;
- CI gates introduced or strengthened;
- issue-to-fix / PR-to-review / release-to-maintenance sequences;
- sustained maintenance of the same project or subsystem;
- automation replacing repeated manual steps;
- documentation/changelog updates that track architectural or behavioral changes.

These signals do not prove AI use. They describe how work is carried through. AI usage should be explicit provenance only when known or user-confirmed.

## What Jev should expand

Jev must not answer facts that GitTeach can compute directly, such as `does this repo contain Rust?`.

Jev is useful for bounded interpretation questions such as:

- Does repeated evidence support an automation-oriented development tendency?
- Is testing/verification a recurring practice across independent projects?
- Does this developer's project history lean toward developer tooling rather than application-only work?
- Is there evidence of long-term maintenance rather than prototype-only activity?
- Do several projects show migration/refactoring work with compatibility safeguards?
- Does this project exhibit an observability/instrumentation practice?
- Does the evidence support classifying this project as an IDE/tool, game tool, library, service, etc. when manifests alone are ambiguous?
- Is a claimed LinkedIn skill supported, unsupported by available repos, or simply unverifiable from connected evidence?

Every Jev observation remains evidence-bounded and may abstain.

## Role of the conversational LLM

The LLM is the profile interviewer and synthesizer, not the coder.

It can:

- explain detected statistics and tendencies;
- identify information gaps that repositories cannot answer;
- ask targeted questions about role, intent, responsibility and AI usage;
- reconcile GitHub evidence with optional LinkedIn/user-declared information;
- ask whether a recurring observable pattern is intentional;
- propose profile wording and project highlights from curated evidence;
- help the user choose what to expose publicly.

User answers are stored as self-reported evidence and should remain distinguishable from independently observed evidence.

Example questions:

- `Across five projects I see custom automation scripts. Is reducing repetitive manual work a deliberate part of how you develop?`
- `This project has repeated migration + regression-test cycles. Were you mainly defining direction, reviewing generated work, debugging, implementing directly, or a mix?`
- `Your LinkedIn lists frontend development, while recent repositories lean toward developer tooling and systems work. Is that a real shift you want reflected in the profile?`
- `I see Rust in several maintained projects. Do you want it represented as recent working experience, or is it incidental to those projects?`

## Optional LinkedIn/profile-source role

LinkedIn or similar sources are declarations about career history, roles, education and skills. They complement repository evidence; they are not an authority over it.

GitTeach can classify a statement as:

- declared + repository-supported;
- declared + not observable in connected repos;
- repository-supported + not currently declared;
- contradictory/ambiguous and worth asking about.

`Not observable` must never be presented as `false`.

## Profile output model

The central profile should contain several distinct sections rather than one synthetic score:

### Technology footprint

Languages, frameworks and tools with recency, project count and evidence coverage.

### Project/domain fingerprint

What kinds of things the person repeatedly builds: developer tools, games/mods, libraries, web apps, infrastructure, graphics, AI tooling, etc.

### Development tendencies

Repeated patterns such as automation, testing, documentation, observability, maintenance and experimentation.

### Delivery and maintenance history

Project longevity, releases, return-to-project behavior, fixes, migrations and sustained ownership/contribution.

### Collaboration footprint

PR/review/issue activity and multi-contributor work when available.

### AI workflow

Only when known: human, AI-assisted, mixed, unknown; plus self-reported or observable supervisory practices. Never estimate a fake `percent human code`.

### Confidence/provenance

Why GitTeach believes each profile statement, what is deterministic, what is semantic, what is self-reported and what remains uncertain.

## WidgetForge integration

WidgetForge should consume stable profile statistics/tendencies rather than re-analyze repositories.

Useful widget families include:

- language/technology evolution over time;
- project-domain mix;
- active/maintained project timeline;
- automation/testing/documentation footprint;
- release and maintenance cadence;
- current project cards;
- contribution visualizations such as the commit snake;
- development-tendency radar/bar views where values mean observed prevalence, not skill level;
- evidence-backed highlights and milestones.

The user controls which widgets and claims become public.

## Product success criterion

A useful GitTeach profile should let a stranger understand:

1. what this developer tends to build;
2. which technologies repeatedly appear in real work;
3. how they tend to carry projects from idea to maintained result;
4. what has changed over time;
5. which statements are observed, interpreted or self-reported;
6. why each important statement exists;
7. how the developer chooses to present that identity visually.

That remains useful even in a future where AI writes most implementation code.
